路由配置转菜单数据 ​

本节目标：理解“路由配置转菜单数据”的核心思路，并能把它用于实际开发或面试表达。 结论：你的“从路由生成菜单”的思路可行，但在大项目里建议做 3 个升级：

  1. 以 meta 作为单一事实来源（title、icon、order、hide、roles、audience 等）；
  2. 稳定的路由分区定位（不要用 includes('public')，而是按根节点 name/路径定位或用 meta.area）；
  3. 一致的树归一化（过滤、排序、单子节点扁平化、角色过滤、i18n 标签回退等）。 下面只给需要修改/新增的代码片段，复杂逻辑上一行有注释。

① 路由 meta 约定（建议逐步补齐） ​

ts
// 复杂逻辑：用 meta 作为菜单的单一事实来源（保持向下兼容你现有的 orderIndex/hiddenInMenu）
meta: {
  title: '仪表板',        // i18n key 或文案
  icon: 'dashboard',      // 图标标识
  order: 1,               // 排序（优先用它；没有则回退到 orderIndex）
  hideInMenu: false,      // 替代 hiddenInMenu
  requiresAuth: true,     // 登录要求（守卫用）
  roles: ['CUSTOMER'],    // 角色要求（守卫/菜单过滤）
  audience: 'customer',   // 人群标记（菜单分区/埋点）
}

③ 菜单构建核心：过滤 + 排序 + 扁平化 + 角色过滤 ​

ts
// 复杂逻辑：当前用户角色（用于菜单过滤；按你的 store 改取值）
const getUserRoles = () => {
  try {
    return JSON.parse(localStorage.getItem('roles') || '[]') as string[]
  } catch {
    return []
  }
}
// 复杂逻辑：判断路由是否显示在菜单中
const isVisibleInMenu = (r: RouteRecordRaw) => {
  const m = r.meta || {}
  // 兼容字段：hideInMenu 优先，其次 hiddenInMenu
  if (m.hideInMenu === true || (m as any).hiddenInMenu === true) return false
  // 有标题或有子项才展示
  return Boolean(m.title || (r.children && r.children.length > 0))
}
// 复杂逻辑：角色过滤：当声明了 roles 时，用户需具备其一
const passRole = (r: RouteRecordRaw) => {
  const need = (r.meta?.roles as string[] | undefined) || []
  if (!need.length) return true
  const mine = getUserRoles()
  return need.some((x) => mine.includes(x))
}
// 复杂逻辑：排序值：优先 meta.order，其次 meta.orderIndex，兜底 99
const getOrder = (r: RouteRecordRaw) => {
  const m = r.meta || {}
  const o = (m as any).order ?? (m as any).orderIndex
  return Number.isFinite(o) ? Number(o) : 99
}
// 复杂逻辑：菜单项 label：优先 meta.title，其次 name 衍生 i18n key
const getLabel = (r: RouteRecordRaw) => (r.meta?.title as string) || `menu.${String(r.name || '')}`
// 复杂逻辑：收敛“叶子”：有可见子项则为分组；否则视为叶子（component 存在与否不再作为判断条件）
const getVisibleChildren = (r: RouteRecordRaw) =>
  (r.children || []).filter((c) => isVisibleInMenu(c) && passRole(c))
// 复杂逻辑：单子节点扁平化：分组只有 1 个子项时，直接用子项代替父项
const flattenIfSingle = (item: MenuProps) => {
  if (item.children && item.children.length === 1) return item.children[0]
  return item
}
ts
// 复杂逻辑：路由树 -> 菜单树（递归）
function buildMenu(nodes: RouteRecordRaw[]): MenuProps[] {
  const list = nodes
    .filter((r) => isVisibleInMenu(r) && passRole(r))
    .map<MenuProps>((r) => {
      const children = getVisibleChildren(r)
      const item: MenuProps = {
        key: String(r.name || r.path),
        label: getLabel(r),
        orderIndex: getOrder(r),
        // 复杂逻辑：icon：优先 meta.icon；回退到你原先的命名方式
        icon: (r.meta?.icon as string) || `icon-menu.${String(r.name || '')}`,
      }
      if (children.length) item.children = buildMenu(children)
      return flattenIfSingle(item)
    })
    .sort((a, b) => a.orderIndex - b.orderIndex)
  return list
}

⑥ 如果需要“按分区产出多套菜单”（公共/IB/更多） ​

ts
// 复杂逻辑：可根据 audience 再筛一层（如果你想把公共区再拆子菜单）
function buildAudienceMenu(nodes: RouteRecordRaw[], audience?: string) {
  const filtered = audience
    ? nodes.filter((r) => !r.meta?.audience || r.meta?.audience === audience)
    : nodes
  return buildMenu(filtered)
}

为什么这套是“大厂实践” ​

  • 单一事实来源：菜单的 title、icon、顺序、隐藏、角色，全在 meta；页面与导航信息同构，减少分散配置。
  • 稳定的分区定位：明确以根节点 name/路径作为锚点，避免 includes('public') 的模糊匹配。
  • 一致的归一化：过滤（可见/角色）→ 排序 → 单子节点扁平化，保证菜单稳定与干净。
  • 易扩展：后续接入 i18n、埋点、A/B 实验，只需在 meta 增加字段即可。
  • 低耦合：不需要在菜单层面解析 redirect，减少与路由跳转策略的耦合。
