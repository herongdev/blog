# 规模与性能验证

2026-09-04，在 macOS arm64、Node.js 22.22.3、Chrome 150.0.7871.189 上执行。测试使用独立浏览器上下文和模拟模型，不调用真实 API。以下是本机固定样本观测，不是容量上限或服务端并发测试。

| 样本                        | 准备与首次整理 | 刷新恢复 | 首次关键词检索 | GC 后页面 JS 堆：恢复 / 搜索后 |
| --------------------------- | -------------- | -------- | -------------- | ------------------------------ |
| 10000 条会话，每条 1 条消息 | 19940ms        | 162ms    | 318ms          | 5.52 / 6.20MB                  |
| 1 条会话，2000 条消息       | 318ms          | 98ms     | 202ms          | 6.10 / 6.41MB                  |
| 1 条会话，200 条带图消息    | 256ms          | 78ms     | 207ms          | 5.09 / 5.49MB                  |

万条样本中，造数 421ms，首次导航、迁移与恢复 19484ms，数据库结构升级本身约 0.7ms。相比上一轮约 67 秒的总准备时间，主要减少了三字符多值索引的写入。首次整理仍可能较长，因此显示批次进度，关闭后可继续；每批数据和游标共同提交。

搜索保留独立文本表，每批读取 256 条记录。命中较少时按 ID 读取摘要，命中较多时分批关联，再用有界堆排序。缓存只保留最近一次查询的前 1000 条摘要与文本 ID，当前页才读取片段。移除三字符索引后，关键词首查是文本表扫描，数据继续增长时需要重新评估搜索方案。

两千条消息样本的一次草稿修改，提交的对象合计 736 个 JSON 字符，未重写历史消息或图片。DOM 中只挂载 7 条消息；图片样本为 6 条。活动展开与表格页码采用最多 200 项的会话内缓存，不保留正文副本。

堆读数来自 Chromium CDP 在垃圾回收后的页面执行上下文，不包含完整进程、Worker 或图片解码内存。此前约 23MB 的未统一 GC 单次读数不能用于证明泄漏。当前仍整体读取选中会话的消息；没有声称内存与历史长度完全无关。

## 复现

```bash
PERF_RUN=1 PERF_LABEL=delivery PLAYWRIGHT_CHANNEL=chrome npm run test:e2e -- tests/e2e/performance-baseline.spec.ts --workers=1
```

PowerShell 先分别设置 `$env:PERF_RUN="1"`、`$env:PERF_LABEL="delivery"`，需要本机 Chrome 时设置 `$env:PLAYWRIGHT_CHANNEL="chrome"`，再执行同一 npm 命令。默认使用 Playwright Chromium 时省略 Chrome 变量。输出位于 `output/performance/delivery/`，该目录不随源码交付。

`migrationMs` 包含造数、导航和等待，`migrationPhases` 将造数与首次载入分开，`databaseUpgradeMs` 单列结构事务；搜索和保存时间包含防抖、批处理及 UI 等待。`serializedChars` 不是磁盘字节数，Blob 另以 `blobBytes` 统计。图片为确定性生成的 64×64 PNG，不代表手机原图。需重复采样后才能给出稳定分位数结论。

迁移中断、v4 分表记录升级、虚拟卸载后的交互状态和表格缩短滚动见 `tests/e2e/migration-and-view.spec.ts`。首次载入、搜索、导出、停止与重试继续纳入完整浏览器回归；最新验收统计以 [试岗交付说明](试岗交付说明.md) 为准。
