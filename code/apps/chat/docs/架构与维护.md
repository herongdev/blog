# 架构与维护

当前采用业务模块优先的轻量架构。聊天和模型设置分别归组，模块内部按视图、运行控制、服务适配和纯状态划分职责。`app` 组合两项业务，`shared` 保存前后端协议。新增功能时有明确归属和检查规则。

## 目录及依赖方向

```text
src/
  main.tsx
  app/                          页面组装与跨业务协调
    App.tsx + App.module.css
    ChatHeader.tsx + ChatHeader.module.css
    useChatWorkspace.ts
  components/                   跨业务公共 UI（Select、Icon、WindowedList），不依赖业务
  features/
    chat/
      components/               消息、活动、引用、输入、侧栏及 CSS Modules
      hooks/                    生成任务生命周期、阅读跟随、历史按需加载
      services/                 本地回放、API 事件流、本地数据库与搜索线程
      state/                    reducer 与纯状态查询
      lib/                      引用转换、Markdown 修复、上下文提取及单测
      types.ts                  客户端消息、会话、演示场景
    model-settings/
      components/               设置弹窗、模型选择及 CSS Modules
      hooks/                    配置加载、刷新与取消
      services/                 获取公开模型元数据
  hooks/                        通用复制、文本框测量、虚拟列表测量
  i18n/                         类型安全文案、插值、界面翻译与错误兼容适配
  preferences/                  语言与主题策略、存储、系统监听、偏好窗口
  styles/                       设计令牌、基础规则、共享视觉及浮层几何适配
shared/
  contracts/                    请求、事件、公开元数据与运行时校验
  transport/                    SSE 解码与分帧封装
  async/                        可取消等待
server/
  index.ts                      读取环境配置、启动 Nest 与关闭钩子
  app.ts + app.module.ts         应用组装、模块注册、静态资源
  chat/                         Controller、Service、请求校验 Pipe、聊天策略
  model-providers/              模块公开服务、私有配置与厂商适配
  http/                         本机访问边界、异常 Filter、SSE 连接管理
  common/                       服务端公共错误类型
tests/
  integration/                  真实附件、API、传输边界
  architecture/                 导入规则与运行环境约束的反例测试
  e2e/                          浏览器行为、隔离测试服务与公共测试工具
scripts/eslint/architecture.mjs  模块边界检查及公开文件清单
scripts/vite/                   首屏偏好引导脚本的构建与注入
third_party/                    固定版本开源源码与许可证
```

允许的主要调用路径：`app → feature 的公开文件 → feature 内部实现 → shared`。视图把用户动作交给回调；业务 Hook 调用服务并派发事件；服务统一输出 `ChatEvent`；reducer 只计算状态。`server → shared` 共享协议，浏览器通过 HTTP 访问服务端。

聊天与模型设置不互相导入；`useChatWorkspace` 负责组合它们。公共 components、通用 Hook 和 styles 不依赖具体业务，业务模块不反向依赖 `app`，共享协议不依赖客户端消息模型。

`i18n` 和 `preferences` 是客户端公共能力，不导入 app 或 feature。`PreferencesProvider` 在 main 中管理偏好并提供翻译上下文，展示组件通过 `useI18n` 取文案，不接管会话状态。纯偏好策略、浏览器副作用、窗口视图与 CSS Modules 分文件维护。首屏引导脚本复用同一套偏好解析逻辑，在 React 加载前设置根节点属性；构建注入位于 `scripts/vite/preferences-bootstrap.ts`。扩展入口与边界见 [多语言与主题](多语言与主题.md)。

## 公开入口和路径别名

公开入口是少量明确文件，由 `scripts/eslint/architecture.mjs` 的 `publicFeatureFiles` 检查。聊天模块公开五个页面组件（Sidebar、Welcome、ChatViewport、MessageList、Composer）、两个业务 Hook、types 和 selectors；模型设置公开两个组件与 useProviders。消息内部渲染器、reducer 和服务仍属模块内部。

不使用汇总全部导出的 `index.ts`；例如应用直接导入 `@/features/chat/components/MessageList`，MarkdownContent 保留动态导入。新增公开入口时先确认其他模块确实需要，再更新清单与对应边界测试。

| 别名       | 指向           | 用法                                           |
| ---------- | -------------- | ---------------------------------------------- |
| `@/`       | `src/`         | app 访问 feature，业务组件复用通用 Hook 和样式 |
| `@shared/` | `shared/`      | 客户端访问协议与通用工具                       |
| `@vendor/` | `third_party/` | 仅指定封装访问内置源码                         |

模块内部优先使用相对路径。TypeScript 在 `tsconfig.base.json` 声明别名，Vite/Vitest 使用相同目标；ESLint 读取 TypeScript 配置，将相对路径和别名解析为同一个依赖目标。服务端继续使用相对导入，运行不依赖 Vite。

## 组件、状态与样式边界

- 展示组件接收明确 props。正文草稿和已读取的文本与图片附件纳入会话状态，由 `useChatStorage` 与 `chatStorage` 按消息和附件分表保存至 IndexedDB；Composer 通过回调更新草稿。引用页码、文件读取和局部展开状态留在组件或专用 Hook。复制反馈和文本框高度分别使用通用 Hook。恢复、冲突和失败规则见 [聊天记录与本地保存](聊天记录与本地保存.md)。
- 生成状态和任务对象由 useChat 按会话 ID 管理，单条聊天内防重入、跨聊天独立运行；后台生成正文保持驻留，组件不导入完整控制器或直接请求服务。异步会话打开由 `useConversationNavigation` 管理请求版本、取消和错误；读取完成只允许最新导航激活会话。`ConversationOpenStatus` 通过 props 展示加载、失败与重试，错误不依赖当前会话 ID。纯状态、转换和服务层不反向引用 React、Hook、组件或样式。
- 组件的样式、响应式规则与 TSX 同目录。公共外观在 `src/styles/primitives.module.css`，设计变量在 tokens，基础重置和焦点规则在 global。
- 布局密度使用独立的 `--density-*` 语义间距令牌，组件只在 gap、padding、margin 中消费；基础 space、字体、图标和布局宽度不随密度缩放。策略与持久化复用 preferences，首屏同步应用 `data-density`。具体边界见 [布局密度](布局密度.md)。
- Markdown 插件类名仅在 Markdown 容器内用 `:global` 适配。正文高亮通过 `data-citation-open` 读取引用状态，不引用其他组件生成的类名。
- 颜色、字号、留白、圆角、阴影、层级、动画和布局尺寸从 `tokens.css` 读取，CSS Modules 负责组合。`Select/useSelect.ts` 管理菜单交互，`Select.tsx` 负责语义结构，`Select.module.css` 负责外观。图标通过公共 `Icon` 的尺寸档位使用令牌。
- 浮层位置与文本框实际高度等测量值留在 JavaScript；浮层静态间距从 CSS 读取。媒体查询只允许 760 / 1100 / 1450 三个约定断点。`styles.test.mjs` 检查硬编码外观值、变量引用、循环依赖及 TSX 样式边界，随 `npm run check` 执行。命名约定、修改方法和 Tailwind 决策见 [样式令牌与选择器](样式令牌与选择器.md)。
- 原始正文与渲染补全内容分开；复制与模型历史使用原文。计时器、观察器和请求都有清理逻辑。

Markdown 延迟加载或渲染失败时，由聊天模块的 `MessageContentBoundary` 接住错误并显示持续更新的原文；网络请求和会话状态不进入该组件。来源及回归用例见 [缺陷来源与回归测试](缺陷来源与回归测试.md)。

Markdown 渲染器的组件类型在模块级保持稳定，引用资料通过 Context 更新，避免 references 事件导致弹层重新挂载、丢失页码和焦点。裸链接的中文标点边界由纯 remark 插件处理；流式补全在 lib 内识别代码上下文，补全结果只用于展示，不写回历史。模型配置服务验证公开响应结构，异常时 Hook 保留上一份可用配置。更多复现条件和验证限制见 [回归覆盖矩阵](回归覆盖矩阵.md)。

性能职责按数据、状态和展示分开：`chatDatabase.ts` 管结构升级，`chatMigration.ts` 管可恢复的批次整理，`normalizedRecords.ts` 管消息和 Blob 记录，`conversationDirectory.ts` 管目录游标，`chatCatalog.ts` 管稳定元数据快照，`searchCandidates.ts` 管分批扫描和摘要关联，`chatSearch.worker.ts` 管异步查询与有界结果缓存。`contextBudget.ts` 只计算请求窗口，不更改历史。`markdownBlocks.ts` 复用已完成语法块，`MarkdownTable` 管表格分页；预览 Hook 管 Object URL 生命周期，`messageViewCache.ts` 有界保存虚拟卸载后的活动展开与页码。具体限制和复现命令见 [聊天记录与本地保存](聊天记录与本地保存.md)。

## NestJS 后端职责

后端是 NestJS 12 的模块化单体，使用 Express 适配器。`AppModule` 组装 `ChatModule`；聊天模块导入 `ModelProvidersModule`，只通过它导出的 `ModelProvidersService` 查询配置和调用模型。模型模块同时提供 `/api/providers` 控制器。服务实例属于各自的应用容器，测试可以为每个应用注入独立的 `env`、`fetcher` 和超时时间。

- `server/app.ts` 创建并初始化 Nest 应用，注册统一前缀、中间件和异常 Filter；`server/index.ts` 监听端口并启用关闭钩子，只有开发模式加载个人环境文件。`common/runtime-config.ts` 校验监听地址、来源、端口、超时和并发配置。
- `ChatController` 接收 HTTP 参数并连接流式响应；`ChatRequestPipe` 使用 `shared/contracts/chatRequestSchema.ts`。`ChatRequest` 和远程厂商 ID 从该 schema 推导，前端继续通过原有类型入口引用。
- `ChatService` 检查模型是否配置、模型名和最后一条消息，再传入 `chat.policy.ts` 的提示词。检查在 SSE 响应头发送之前完成，失败仍返回原有 HTTP 状态与 `{ error }` JSON。
- `ModelProvidersService` 管理私有配置和上游访问依赖；`upstream.ts` 只处理厂商请求格式、调用与事件转换，不读取产品提示词，也不持有 Express 响应。
- `http/sse.ts` 为每个请求创建独立的 AbortController，负责响应头、背压、超时、连接断开和终态收尾。`done` 或 `error` 后结束迭代，清理计时器、监听器与上游资源；关闭应用也会关闭连接并取消上游。
- 流式阶段只有明确的 `StreamError` 可以向用户传递消息，其他异常转换成固定文案。普通 HTTP 异常统一由 `ApiExceptionFilter` 转换，保留 400、403、413、503 等语义，不输出请求体或凭据。

请求诊断由 `http/request-diagnostics.ts` 在 API 入口生成编号，SSE 传输层记录实际终态，正常启动入口注入结构化日志收集器。客户端服务把响应头转换为 metadata，组件不依赖 HTTP。详见 [请求诊断与草稿](请求诊断与草稿.md)。

依赖方向由 ESLint 检查：服务端模块不得反向依赖应用入口；模型模块不得依赖聊天策略和 HTTP；`http`、`common` 不得依赖业务模块；业务 Service 不得引用 Express 或 HTTP 连接封装。客户端和共享协议不得导入 Nest。

开发运行使用 `tsx --tsconfig tsconfig.server.json`。服务端和测试开启 legacy decorators，所有构造参数显式使用 `@Inject`，不依赖 `emitDecoratorMetadata`；Vitest 的 Oxc 和生产构建的 esbuild 使用一致的装饰器语义。保留现有 Zod，无需另外维护一份 class-validator DTO。

`npm run build` 先类型检查，再构建 `dist/client` 和 `dist/server`；后端构建保留 npm 运行依赖为外部依赖。`npm start` 直接运行 `node dist/server/index.js --production`，静态根目录只指向 `dist/client`。浏览器回归从 `dist/server/app.js` 加载编译后的 Nest 应用，使用空环境和禁止真实上游请求的 fetcher；测试不经过读取环境文件的生产入口。

`GenerationCapacity` 按应用实例管理活跃生成名额，Controller 在 SSE 前执行准入，使用 `finally` 释放名额；容量不足返回 429。`HealthController` 提供不调用上游的 `/api/healthz`。来源中间件支持配置后的精确 Origin 匹配，公网访问认证在 Caddy 入口完成。配置、镜像、代理和发布恢复见 [容器部署](容器部署.md)。

当前是可部署的单实例应用，聊天历史通过浏览器 IndexedDB 持久化，没有账户、服务端历史数据库或公网用户隔离。尚未进行服务端并发容量压测；浏览器固定规模样本见存储文档。

框架参考：[模块](https://docs.nestjs.com/modules)、[自定义 Provider](https://docs.nestjs.com/fundamentals/custom-providers)、[Controller](https://docs.nestjs.com/controllers)。

## 类型环境与可执行检查

`tsconfig.json` 是编辑器识别的项目入口；`npm run typecheck` 分别检查三个配置：

| 配置                   | 范围                       | 环境                                       |
| ---------------------- | -------------------------- | ------------------------------------------ |
| `tsconfig.client.json` | src（排除单测）与 shared   | DOM、Vite 客户端；不自动加载 Node 全局类型 |
| `tsconfig.server.json` | server、shared、Vite 配置  | Node；不加载 DOM 库                        |
| `tsconfig.tests.json`  | 单测、集成、E2E 和测试配置 | 测试需要的 Node 与 DOM                     |

共享代码在客户端和服务端两个环境下都接受检查。客户端不引入 Node 全局类型，服务端不引入 DOM 类型。ESLint 另外限制环境全局对象、Node 内置导入、前后端相互引用、跨 feature 私有依赖及展示组件直接 fetch。

ESLint 同时检查静态导入、再导出和动态导入。客户端动态路径必须静态可解析。测试可以访问内部实现；规则正反例覆盖相对路径、别名、扩展名、再导出、动态导入、环境全局对象和 Nest 模块的依赖方向。

本机已有 Google Chrome 时，可用 `PLAYWRIGHT_CHANNEL=chrome npm run test:e2e`。CI 使用 Playwright 安装的 Chromium，已执行环境见 [最新验收记录](试岗交付说明.md#四实际验收记录)。

E2E 默认占用本机 4173，可用 `E2E_PORT=4174 npm run test:e2e` 调整。端口被占用时直接报错，不复用正在运行的开发服务。每条测试拥有独立浏览器上下文。

浏览器用例验证流式引用分页与停止隔离、Markdown 代码复制、异常重试与空结果、模型配置和请求选项、手机侧栏与浮层、阅读保护与尺寸变化。测试服务显式传入空配置，不加载 `.env.local`；浏览器阻止未声明的远程请求，模型用例以固定 SSE 响应验证 UI 到请求的链路。编译后的 Nest API 另有浏览器测试，检查元数据、错误格式及静态文件边界。集成测试覆盖真实 Nest 路由、上游适配、超时、断开取消、应用关闭、配置隔离与错误脱敏。

`.github/workflows/ci.yml` 在 push / pull request 运行安装、格式、lint、Vitest、类型/构建和 Chromium E2E。报告、失败截图和 trace 输出到被忽略的 `output/playwright/`，CI 保留报告 7 天。工作流已配置，本地通过不代表 GitHub 云端已经执行。

浏览器自动化目前覆盖 Chromium 的桌面与手机尺寸；没有宣称覆盖 Firefox、Safari 或全部输入。只有实际新增功能或修复风险时扩充验证。
