# 请求诊断与草稿保护

这次改动补强会话切换和异常排查。原附件、正常发送与流式引用仍是验收主线，没有新增依赖。

## 草稿如何保留

草稿正文和已读取的文本和图片附件按 `conversationId` 纳入会话状态，通过 props 交给 `Composer`。主动发送的状态更新只清空当前会话草稿；停止、重试和未配置时打开设置都不会消费草稿。

输入组件通过 `useChat.setDraft` 和 `setAttachments` 更新对应会话。纯状态更新同时维护 `hasDraft`，侧栏据此保留尚未发送的会话入口。未发送草稿不会进入模型请求历史；清空后离开的空会话继续隐藏。

会话和草稿会自动保存到当前浏览器的 IndexedDB，刷新或重新打开相同地址后恢复。保存失败时提示重试或导出备份。详细的数据结构、刷新日志和多标签页冲突策略见 [聊天记录与本地保存](聊天记录与本地保存.md)。

| 修改入口                                                               | 职责                                 |
| ---------------------------------------------------------------------- | ------------------------------------ |
| `src/features/chat/components/Composer.tsx`                            | 展示草稿及附件，通过回调交付用户编辑 |
| `src/features/chat/hooks/useChat.ts`、`state/chatReducer.ts`           | 更新会话草稿，接受发送时清空当前草稿 |
| `src/features/chat/hooks/useChatStorage.ts`、`services/chatStorage.ts` | 初始化恢复、事务保存、冲突及失败保护 |
| `src/features/chat/components/Sidebar.tsx`                             | 保留有草稿的空会话入口               |
| `src/app/App.tsx`                                                      | 传入会话 ID 与回调，保持输入组件身份 |

`DRAFT-001` 已在改动前构建中复现失败：切回甲会话时预期恢复两行草稿，实际为空。修复后回归同时检查内容、请求数量、重试问题及其他会话的草稿，而不只检查一个状态字段。

## 会话切换的画面稳定性

打开历史时先保留当前正文和草稿，目标读取完成后再切换。快速读取不显示加载条；等待超过 200 毫秒才显示可取消的浮动提示，失败时立即显示重试提示。提示不占据消息区布局，不挤压正文或输入区，也不改变当前阅读位置。这个延迟只影响提示，不延迟实际打开。

切换、新建、取消或卸载会清理提示计时器；旧读取即使完成，也不能覆盖后续导航。进入新会话时在绘制前完成首次滚动定位，继续复用原有流式跟随与手动阅读规则，不修改上游滚动库源码。对应回归在 `history-navigation.spec.ts`：检查快速读取期间未挂载加载提示、新正文首次提交时已定位、慢读取前后视口尺寸与滚动位置不变，以及取消后的迟到读取和提示隔离。

## 图片请求与等待阶段

远程请求依次显示“正在准备附件”（有图片时）、“正在发送请求”、“正在等待模型响应”。最后一个阶段表示收到本服务的 SSE 响应头，还不能证明模型已返回内容；思考、工具或正文到达后，由实际内容状态接管显示。本地 JSON 回放不显示网络阶段。

浏览器从开始发送请求到收到响应头最多等待 120 秒，覆盖上传和等待本服务接收的时间；超时取消请求并保留问题供手动重试，不自动重复调用模型。服务端接收并校验请求后，另有生成超时（线上为 120 秒）。两者起点不同，不是整个过程合计最多 120 秒；浏览器附件读取不计入发送计时。

图片从 IndexedDB 还原后随选中的历史重新发送。三轮中只有首轮包含一张图片时，第三轮请求仍只有一张历史图片，不会因轮数重复三份；新增图片及正文会扩大上下文。没有静默丢弃历史图片、降低图表清晰度或跨请求图片缓存。`qwen3-vl-plus` 关闭深度思考时显式传 `enable_thinking: false`，三轮图片上下文由模拟上游回归覆盖，不代表真实模型的延迟承诺。

## 如何关联一次错误

每次 `/api` 请求由服务端生成新的 UUID，通过 `X-Request-Id` 响应头返回。入口早于来源和请求体校验，因此普通 JSON 拒绝和 SSE 流式失败都可以关联。不接受调用方指定的编号。

浏览器传输层将有效编号转换为 `metadata` 事件；reducer 将它存入对应的助手消息。错误时可以展开“问题详情”、复制编号。重试会创建新消息并使用新编号。没有收到响应头、没有有效编号，或者使用本地附件回放时，不显示编号。

调用链：`requestDiagnostics → X-Request-Id → streamAPI → metadata → useChat → chatReducer → MessageDiagnostics`。

正常启动入口 `server/index.ts` 将一条请求结束记录输出为一行 JSON。运行时可由终端或部署环境收集标准输出；`createApp` 支持注入 `requestLogger`，测试使用内存收集器。未提供收集器时仍返回编号，但不写日志。

示例结构（数值仅示意）：

```json
{
  "event": "api_request",
  "at": "2026-09-03T15:00:00.000Z",
  "requestId": "cd46aacb-714d-4b79-a061-c99d99dbe184",
  "method": "POST",
  "route": "/api/chat",
  "statusCode": 200,
  "outcome": "timeout",
  "durationMs": 120003
}
```

| 字段                                   | 含义与边界                                                                                                    |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `requestId`                            | 本次 API 请求的关联编号；不是用户 ID、会话 ID 或附件 recordId                                                 |
| `statusCode`                           | HTTP 状态，SSE 开始后仍可能是 200                                                                             |
| `outcome`                              | 传输/生成结束结果，见下表                                                                                     |
| `durationMs`                           | 进入诊断中间件至服务端结束/连接关闭的单调时钟耗时                                                             |
| `acceptedMs`                           | 进入中间件至请求体解析、业务校验完成；不含 Nginx 在转发前缓冲请求体的时间                                     |
| `upstreamHeadersMs` / `upstreamStatus` | 从同一起点至收到模型服务响应头的耗时及其 HTTP 状态；上游未返回头则省略                                        |
| `firstActivityMs`                      | 首次写入有效正文、思考或工具事件后的耗时；没有活动则省略                                                      |
| `provider` / `model` / `thinking`      | 通过服务端配置校验的模型及请求开关；不是模型输出内容                                                          |
| `messageCount` / `imageCount`          | 本次发送的上下文消息数及图片数                                                                                |
| `imageBytes` / `textBytes`             | 图片 data URI 的 ASCII 编码长度总和（含 Base64 前缀）、消息正文 UTF-8 字节数；不等于 token 数或完整 HTTP 大小 |
| `firstTextMs`                          | 首次写入包含非空白正文的事件并处理背压后的耗时；没有正文时省略                                                |

`firstTextMs` 不包含纯思考、工具或响应头，不等于模型 token 指标或浏览器首次绘制时间。`finish` 表示数据交给系统传输，不能证明用户已读到。参见 [Node.js HTTP 生命周期](https://nodejs.org/api/http.html#event-finish_1)。

| outcome                               | 含义                                                       |
| ------------------------------------- | ---------------------------------------------------------- |
| `completed`                           | 写出 done，且此前写过非空白正文                            |
| `empty`                               | 写出 done，但没有有效正文                                  |
| `upstream_error`                      | 上游拒绝、解析失败、异常断流或 error 终态                  |
| `timeout`                             | 本服务的生成时间限制触发并取消上游                         |
| `incomplete`                          | 适配器迭代耗尽却没有终态；传输层补一个 error               |
| `disconnected`                        | 响应完成前连接关闭；不能据此断言是用户主动停止还是网络掉线 |
| `success` / `rejected` / `http_error` | 普通 API 的成功 / 4xx / 5xx                                |

`finish` 和 `close` 共用一次性收尾，记录后移除两种监听器。日志只收集字段白名单；不记录提问、回答、思考原文、密钥、原始异常、请求头、查询参数或任意 URL 路径。日志收集器同步抛错不会导致请求崩溃。

Nginx 部署额外写入 `chat.herong.info.timing.log`：包括请求/响应字节数、总耗时和转发至本服务的连接、响应头及响应耗时，使用相同 `requestId` 关联。`appHeadersSeconds` 是 Nginx 等待 Nest 响应头的耗时，不能当作模型首字时间。请求在到达应用前断开可能没有编号；499 仅表示客户端先断开，不能单独定位原因。新日志不包含查询参数、任意路径、客户端 IP 或消息内容；现有普通访问日志仍按 Nginx 的配置记录。

定位时结合 `requestBytes`、应用 `acceptedMs`、`upstreamHeadersMs`、`firstActivityMs`、`firstTextMs` 区分大请求传输、应用接收、上游响应头与内容等待。所有应用耗时使用同一中间件起点；`upstreamHeadersMs - acceptedMs` 同时包含请求准备、上传至上游和上游等待，不是纯模型计算时间。请求日志在结束时输出，生成过程中不会先出现完整结束记录。

这是一项单实例排障能力，不包含集中日志检索、告警、分布式追踪和容量证明。收集器应快速返回；生产高流量时需要单独评估日志输出背压和采样策略。
