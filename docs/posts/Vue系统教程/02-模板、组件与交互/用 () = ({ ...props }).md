# 用 () = ({ ...props })

> 本节目标：理解“用 () = ({ ...props })”的核心思路，并能把它用于实际开发或面试表达。
你的问题是关于为什么在 watch 中使用 () =\> (\{ ...props \}) 而不是直接使用 () =\> props，以及为什么要解构 props。这是一个很棒的问题，涉及到 Vue 的响应式机制和 watch 的依赖追踪原理。我会详细解释原因，并分析两者的区别。

**背景：watch 的依赖追踪**
在 Vue 中，watch 的第一个参数是一个“源”（source），它可以是一个函数（返回需要监听的值）、一个 ref、一个响应式对象，或者一个简单的值。watch 会通过这个源的 getter 函数（例如 () =\> props 或 () =\> (\{ ...props \})）来追踪依赖，只有当 getter 返回的值发生变化时，才会触发回调。

- **props 是一个代理对象**：在 Vue 3 中，props 是通过 reactive 或类似的机制包装的代理对象（Proxy）。它的属性（如 props.value、props.picker）是响应式的，但 props 对象本身的引用是固定的。
- **依赖追踪的粒度**：watch 依赖于 getter 函数的返回值，而不是直接监听对象本身。如果 getter 返回的引用没有变化，watch 不会触发回调。

**直接使用 () =\> props 的问题**
如果你在 watch 中直接写：
typescript
CollapseWrapCopy
watch( () =\> props, (newProps) =\> \{ _// 同步逻辑_ \},)
会发生什么？

1. **props 的引用不变**
    - props 是一个固定的代理对象，它的内存地址在组件生命周期内不会改变。即使 props.value 或 props.picker 的值变了，props 本身的引用仍然是同一个。
    - () =\> props 每次执行都返回同一个对象（同一个引用），而 watch 只关心 getter 返回值的变化。由于引用没变，watch 不会认为有任何变化，也就不会触发回调。
2. **无法检测内部属性的变化**
    - watch 默认是浅层监听（shallow watch），它不会深入追踪 props 内部属性的变化（除非显式设置 deep: true）。
    - 因此，即使 props.value 从 '2023-01-01' 变成了 '2023-02-01'，watch(() =\> props, ...) 不会触发，因为它只看到 props 的引用没变。
3. **结果**
    - 使用 () =\> props，watch 回调几乎永远不会执行，除非 props 本身被完全替换（这种情况在 Vue 组件中几乎不可能发生，因为 props 是由父组件传入的代理对象）。

**使用 () =\> (\{ ...props \}) 的原因**
现在来看为什么用 () =\> (\{ ...props \})：

1. **解构创建新对象**
    - \{ ...props \} 使用展开运算符（spread operator）将 props 的所有属性复制到一个新的普通对象中。
    - 每次 props 的某个属性（如 props.value）发生变化时，\{ ...props \} 会生成一个新的对象，这个新对象的属性值会反映最新的 props 值。
    - 因为每次返回的是一个新对象（引用不同），watch 可以检测到变化并触发回调。
2. **依赖追踪生效**
    - 在 () =\> (\{ ...props \}) 中，Vue 的响应式系统会在执行 getter 时访问 props 的每个属性（如 props.value、props.picker），从而将这些属性注册为依赖。
    - 当这些属性中的任何一个发生变化时，getter 返回的新对象内容会不同，watch 就会触发。
3. **例子**
    - 假设 props.value 从 '2023-01-01' 变为 '2023-02-01'：
        - () =\> props 返回的始终是同一个 props 引用，watch 不触发。
        - () =\> (\{ ...props \}) 返回 \{ value: '2023-01-01', ... \}，然后变为 \{ value: '2023-02-01', ... \}，引用变了，watch 触发。

**是否可以用 deep: true 替代解构？**
你可能会想：如果直接用 () =\> props 并加上 \{ deep: true \}，会不会解决问题？
typescript
CollapseWrapCopy
watch( () =\> props, (newProps) =\> \{ _// 同步逻辑_ \}, \{ deep: true \},)

- **效果**：加上 deep: true，watch 会深度监听 props 的所有属性变化，即使 props 的引用没变，只要内部属性（如 props.value）变了，回调也会触发。
- **问题**：
    1. **性能开销**：深度监听会递归遍历 props 的所有嵌套属性（包括 locale 这样的对象），可能导致不必要的性能消耗，尤其当 props 包含复杂结构时。
    2. **不精确**：你可能只关心某些属性的变化，但 deep 会监听所有属性，包括那些你不希望同步的（如 locale 如果它不常变）。

相比之下，() =\> (\{ ...props \}) 是浅层复制，只关心 props 的第一级属性，既精确又高效。

**为什么不直接用 props（不包函数）？**
你可能会再问：能不能直接写 watch(props, ...) 而不是 () =\> props？

- **不行**：watch 的第一个参数必须是一个 getter 函数、一个 ref、或一个响应式对象（reactive）。直接传入 props（一个 Proxy 对象）虽然在某些情况下能工作，但 Vue 官方推荐使用 getter 函数来明确依赖。
- **原因**：getter 函数允许你控制哪些值被追踪，而直接传入对象可能导致意外的依赖收集或行为不一致。

**总结：为什么要解构？**

1. **() =\> props 不行**
    - 因为 props 的引用不变，watch 无法检测内部属性的变化，除非加 deep: true，但那样不够高效。
2. **() =\> (\{ ...props \}) 的作用**
    - 解构生成新对象，每次 props 的属性变化时，返回值引用不同，触发 watch。
    - 依赖追踪精确到 props 的第一级属性，性能和行为都更可控。
3. **为什么不直接用 props 或其他方式？**
    - Vue 的响应式机制要求 watch 的源返回可变的值，解构是最简单、直接的办法。

**验证实验**
你可以试试以下代码对比效果：
typescript
CollapseWrapCopy
setup(props, \{ emit \}) \{ _// 测试 1：直接用 props_ watch( () =\> props, (newProps) =\> \{ console.log('props changed:', newProps) \}, )
_// 测试 2：用解构_ watch( () =\> (\{ ...props \}), (newProps) =\> \{ console.log('props destructured changed:', newProps) \}, )
_// 测试 3：加 deep_ watch( () =\> props, (newProps) =\> \{ console.log('props deep changed:', newProps) \}, \{ deep: true \}, )
_// ... 其余代码_\}

- 当 props.value 变化时：
    - 测试 1 不触发。
    - 测试 2 和测试 3 都会触发，但测试 3 的 deep 可能监听过多。

**结论**
() =\> (\{ ...props \}) 是必要的，因为它通过解构创建新对象，让 watch 能正确检测 props 的变化。直接用 () =\> props 不行，除非加 deep: true，但那样会牺牲性能和精确性。解构是目前的最佳实践，既简单又高效，符合 Vue 的响应式设计理念。

是的，你提出的这个观察非常正确！在使用 () =\> (\{ ...props \}) 时，即使 props 的属性没有一个值发生变化，watch 仍然会被触发，因为每次 getter 函数执行都会创建一个新的对象引用。让我详细解释一下这个行为，以及它可能带来的影响和解决方法。

**为什么会这样？**

1. **\{ ...props \} 创建新对象**
    - 每次执行 () =\> (\{ ...props \})，展开运算符 \{ ...props \} 都会生成一个全新的对象，即使 props 的每个属性值完全相同，新对象的内存地址（引用）都会不同。
    - 在 JavaScript 中，对象的相等性是基于引用的，而不是内容的。例如： javascriptCollapseWrapCopyconst obj1 = \{ a: 1 \};const obj2 = \{ a: 1 \};console.log(obj1 === obj2); _// false，因为引用不同_
2. **watch 的触发机制**
    - Vue 的 watch 默认比较 getter 返回值的引用（浅层比较）。如果 getter 返回的对象引用变了，即使内容完全一样，watch 也会认为值“变了”，从而触发回调。
    - 在你的例子中，() =\> (\{ ...props \}) 每次返回一个新引用，watch 无法判断内容是否真的变了，因此总是触发。
3. **例子******假设 props 是 \{ value: '2023-01-01', picker: 'date' \}：
    - 第一次执行：\{ value: '2023-01-01', picker: 'date' \}（引用 A）
    - 组件重新渲染（即使 props 没变）：\{ value: '2023-01-01', picker: 'date' \}（引用 B）
    - 引用 A !== 引用 B，watch 触发。

**这会导致什么问题？**
你说得对，即使 props 的属性没有变化，watch 也会执行回调。这可能带来以下影响：

1. **不必要的执行**
    - 如果回调中包含同步逻辑（比如更新 datepicker 的状态），这些逻辑会重复运行，即使没有实际变化。
    - 在你的代码中，Object.assign 或逐个赋值会反复执行，可能导致性能浪费。
2. **潜在的副作用**
    - 如果回调中有复杂计算或外部操作（比如 API 调用），这种无意义的触发会增加开销。

**如何验证？**
你可以用以下代码测试：
typescript
CollapseWrapCopy
setup(props, \{ emit \}) \{ watch( () =\> (\{ ...props \}), (newProps, oldProps) =\> \{ console.log('watch triggered', newProps, oldProps); \}, ); _// ... 其余代码_\}

- 每次组件渲染（即使 props 没变，比如父组件无关状态更新），watch 都会打印日志，因为新对象引用不同。

**如何解决？**
如果你只想在 props 的内容实际变化时触发 watch，可以采取以下方法：
**方案 1：手动比较内容**
在回调中添加内容比较逻辑，只在值变化时执行同步：
typescript
CollapseWrapCopy
setup(props, \{ emit \}) \{ const datepicker = useDatepicker(_/* ... */_);
watch( () =\> (\{ ...props \}), (newProps, oldProps) =\> \{ _// 比较新旧 props 的内容_ const isChanged = Object.keys(newProps).some( (key) =\> newProps[key] !== oldProps[key] ); if (!isChanged) return; _// 如果没变，直接返回_
_// 只有内容变了才同步_ datepicker.value.value = newProps.value ?? null; datepicker.currentMonth.value = new Date(newProps.currentMonth); datepicker.picker.value = newProps.picker; _// ... 其他同步逻辑_ \}, );
return () =\> (props.render ? props.render(datepicker) : DefaultRender(datepicker));\}

- **优点**：简单，只在内容变化时执行同步逻辑。
- **缺点**：需要手动比较，且对深层对象（如 locale）需要额外处理。

**方案 2：使用 deep 并避免解构**
直接监听 props 并启用深层监听，避免每次创建新对象：
typescript
CollapseWrapCopy
watch( () =\> props, (newProps) =\> \{ datepicker.value.value = newProps.value ?? null; datepicker.currentMonth.value = new Date(newProps.currentMonth); datepicker.picker.value = newProps.picker; _// ... 其他同步逻辑_ \}, \{ deep: true \},);

- **优点**：不需要解构，只有 props 的属性实际变化时才会触发。
- **缺点**：深层监听可能监听过多（比如 locale 的嵌套属性），性能稍低。

**方案 3：使用自定义比较器**
Vue 的 watch 支持自定义 isEqual 函数（在 Vue 3.4+ 中可用），可以精确控制触发条件：
typescript
CollapseWrapCopy
watch( () =\> (\{ ...props \}), (newProps) =\> \{ _// 同步逻辑_ \}, \{ _// 自定义比较器_ flush: 'pre', isEqual: (newVal, oldVal) =\> \{ return Object.keys(newVal).every((key) =\> newVal[key] === oldVal[key]); \}, \},);

- **优点**：精确控制，只有内容变化时触发，不需要手动在回调中比较。
- **缺点**：需要 Vue 3.4+，且对深层对象仍需额外处理。

**方案 4：优化 useDatepicker 的设计**
更彻底的解决方案是调整 useDatepicker，让它直接接受响应式 props，内部处理同步逻辑，而不是依赖外部 watch：
typescript
CollapseWrapCopy
export function useDatepicker(options: Record\<string, any\>, emit) \{ const value = ref(options.value); const currentMonth = ref(options.currentMonth); const picker = ref(options.picker); _// ... 其他 ref_
_// 内部监听 options 变化_ watch(() =\> options.value, (newVal) =\> \{ value.value = newVal; \}); watch(() =\> options.currentMonth, (newVal) =\> \{ currentMonth.value = newVal; \}); watch(() =\> options.picker, (newVal) =\> \{ picker.value = newVal; \}); _// ... 其他 watch_
_// ... 其余逻辑_\}
然后在组件中直接传入 props：
typescript
CollapseWrapCopy
setup(props, \{ emit \}) \{ const datepicker = useDatepicker(props, (event, value) =\> emit(event, value)); return () =\> (props.render ? props.render(datepicker) : DefaultRender(datepicker));\}

- **优点**：逻辑封装在 useDatepicker 内部，组件代码更简洁，watch 只触发必要变化。
- **缺点**：需要修改 useDatepicker，增加其复杂度。

**推荐方案**

- **短期推荐**：方案 1（手动比较内容），简单且立即可用，适合当前代码。
- **长期推荐**：方案 4（优化 useDatepicker），从设计上解决问题，减少外部依赖。

例如，使用方案 1：
typescript
CollapseWrapCopy
watch( () =\> (\{ ...props \}), (newProps, oldProps) =\> \{ const isChanged = Object.keys(newProps).some( (key) =\> newProps[key] !== oldProps[key] ); if (!isChanged) return;
datepicker.value.value = newProps.value ?? null; datepicker.currentMonth.value = new Date(newProps.currentMonth); datepicker.picker.value = newProps.picker; _// ... 其他同步_ \},);

**结论**
是的，() =\> (\{ ...props \}) 会因为新引用导致 watch 每次都触发，即使 props 的值没变。要避免不必要的触发，可以在回调中比较内容，或调整设计让 useDatepicker 内部处理响应性。你的观察非常敏锐，这确实是一个需要注意的细节！有什么其他想法或需求吗？我可以继续帮你优化！
