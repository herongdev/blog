# 万级持仓实时盈亏 + 账户面板派生

> 本节目标：理解“万级持仓实时盈亏 + 账户面板派生”的核心思路，并能把它用于实际开发或面试表达。
完整摸完了。先告诉你结论：**之前亮点 6 提到过，但只是一笔带过，远远不够分量；这块绝对值得独立成一条高位亮点，而且是简历里最值钱的几条之一。**下面给你完整客观评估和成稿。

## 一、这块和之前亮点的重叠度（先把客观情况说清）

之前我在【技术亮点 6】"独立 Web Worker 化的计算密集模块"里只点到了 `openPositionWorker` 的两件事：500ms 节流 emit 和 5 份内部索引。但**完整摸完代码之后，这块至少有 8 个隐藏在代码里的深度细节没有体现**，过于"埋没"了。

更关键的是，"**支持万级订单 + 高频报价 + 多品种实时盈亏**"是 CFD 经纪商面试官最喜欢追问的场景之一，与"行情列表（看盘）"和"SL/TP（下单）"完全不冲突——它对应的是"**仓位侧**"，是三大业务面之一。把它埋在 Worker 那条里非常浪费。

## 二、这块隐藏的工程细节（事实层）

我把整条链路梳理出来，每一项都对应代码里能查到的位置：

### 1）端到端数据流（一图说清）

```
后端列表 (pageSize=99999)
│
├─→ openPositionsRawMap (主线程 Map，原始备份)
├─→ unfoldRows (shallowRef，UI 只读)
├─→ socketStore.updateModulePool('OpenOrder', symbols 去重) ⟵ 订阅池只订有持仓的品种
└─→ worker.initOrder(WorkerInitData[])

socketStore.quoteTick (高频)
│
└─→ 主线程 watch 收集到 openPositionPendingQuotes (Map<SYMBOL, {ask,bid}>)
│ 同品种多次报价覆盖为最新一次
└─→ useIntervalFn(500ms) → worker.sendQuoteBatch

socketStore.orderOperationEvents (中频)
│
└─→ pendingOrderEvents[] 累积
└─→ useIntervalFn(500ms) → worker.sendOrderBatch

Worker 内
│ processOpenOrderData(unfoldRows, quoteMap)
│ ├─ initOrder 用 __profitFactor 重算每张订单 PROFIT
│ ├─ 同品种折叠 buildFoldRowsBySymbol（Decimal 加权开仓价）
│ ├─ updateTotalStats / updateCategoryStats / statsBySymbol
│ └─ markOrderDirty (500ms 节流，只发最新一帧)
│
├─→ 'stats-updated' (实时 emit，账户面板秒级响应)
└─→ 'order-updated' (500ms 节流 emit，避免列表重排抖动)

主线程
├─→ unfoldRows / foldRows (shallowRef，避免对 1 万行做深度响应化)
├─→ totalStats / categoryStats / statsBySymbol (reactive)
└─→ watch totalFloatingPL → 推导 Equity / FreeMargin / MarginLevel%
→ accountsStore.updateAccountWithDynamicInfo
```

### 2）真正"硬核"的 8 个工程细节

| # | 细节 | 代码位置 | 价值 |
|---|---|---|---|
| 1 | **`__profitFactor` 盈亏因子缓存** | `_utils/computed.ts:168-184` | **这是支撑万级订单的灵魂**。首次：`factor = PROFIT / (CLOSE_PRICE - OPEN_PRICE)`；之后每次报价：`PROFIT = factor × (CURRENT_PRICE - OPEN_PRICE)`，把所有币种/合约规模/汇率换算的重计算降级为一次乘法 |
| 2 | **VOLUME 变更触发 factor 失效** | `openPositionWorker.ts:88-95` | `volumeChanged ? undefined : 保留`，业务规则与缓存策略对齐 |
| 3 | **同品种自动折叠 + 净仓位方向 + 对冲识别** | `_utils/computed.ts:120-152、66-89` | Decimal 加权开仓价；净手数为 0 标 CMD=6（对冲组）；多空孤仓识别 `isNetPosition` |
| 4 | **报价 / 订单事件双 channel 独立 batch** | `useOpenPosition.ts:178-214` | 两个独立 500ms `useIntervalFn`，互不阻塞；同 SYMBOL 报价 Map 覆盖去重 |
| 5 | **分级 emit：stats 实时 / orders 节流** | `openPositionWorker.ts:124-141` | `stats-updated` 立即 emit（账户面板秒级响应），`order-updated` 走 dirty + 500ms 节流（避免列表 layout 抖动） |
| 6 | **可视行联动订阅池** | `OpenOrder.vue:390-398` | `handleVisibleDataUpdated` 在 rAF 内把"当前可视品种"推到订阅池，**把 ws 推送量收敛到可视区** |
| 7 | **`shallowRef` 关键性能护栏** | `useOpenPosition.ts:29-30` | 1 万行 × 30 字段如果走 `ref` 深度响应化，光 Proxy 创建就够 50ms；`shallowRef` 把成本降到引用替换 |
| 8 | **切账号清理顺序协议** | `useOpenPosition.ts:154-175` | 先清 UI（防止旧数据残留闪烁）→ 清 store → 清订阅池 → 清两条 batch 缓冲 → 重置统计 → 通知 worker `initOrder([])`，**顺序错了就闪旧数据** |

### 3）派生的"账户实时面板"

`useOpenPosition.ts:235-269` 把 worker 算出的 `totalFloatingPL` 实时推回账户：

```javascript
Equity = Balance + Credit + Commission + Swaps + FloatingPL
FreeMargin = Equity - UsedMargin
MarginLevel% = (Equity / UsedMargin) × 100
```

——这意味着**整个交易终端的"账户净值/可用保证金/保证金水平"都靠这条管线驱动**。这是经纪商客户端最关键的 3 个数字。

## 三、是否单独成亮点？怎么加？

**强烈建议独立成一条 Top 亮点**，理由：

1. **业务面不重叠**：行情列表（看盘）/ SL-TP（下单）/ 万级订单（仓位）—— 三大业务面就齐了；
2. **`__profitFactor` 这种"简化重计算"的巧思**是简历里最值钱的工程细节，一句话能让面试官眼睛亮起来；
3. **派生整个账户面板**这件事一说出来，面试官就知道你"全链路都打通了"；
4. **"万级订单 + 高频报价"**这个具体的数字描述本身就是 CFD 面试官的兴奋点。

**调整策略**：
- **新增一条**核心亮点："万级持仓订单实时盈亏 + 同品种自动折叠 + 账户面板派生"；
- **同时收紧原亮点 6**（独立 Web Worker 化），把"持仓"那段砍掉，让亮点 6 只覆盖"行情 worker / 交易日历 worker"，避免重复抢戏。

排序建议：**这条放 Top 8 的第 3 位**，紧跟在"行情列表"和"SL/TP"之后，把交易终端三件套（看盘/下单/仓位）连成一条故事线。

## 四、可以直接放进简历的两段

### 1）追加到「技术亮点扫描」（升级为第 15 条 / 替代亮点 6 的持仓部分）

【技术亮点 15】万级持仓订单实时盈亏 + 同品种聚合 + 账户面板派生

- **文件位置**：
- `src/views/(public)/trading/_components/order-tabs/OpenOrder.vue`
- `src/views/(public)/trading/_components/order-tabs/composable/useOpenPosition.ts` / `useOpenPostionWorker.ts`
- `src/views/(public)/trading/_components/order-tabs/workers/openPositionWorker.ts`
- `src/views/(public)/trading/_utils/computed.ts`
- **实现内容**：
- **盈亏因子缓存（`__profitFactor`）**：首次计算 `factor = PROFIT / (CLOSE_PRICE - OPEN_PRICE)`，之后每次报价只做 `factor × (CURRENT_PRICE - OPEN_PRICE)` 一次乘法，把所有币种换算 / 合约规模 / 汇率换算等重运算从"每帧每订单"降级为"开仓时一次"；VOLUME 变更时显式失效因子；
- **双 channel 独立批处理**：`socketStore.quoteTick` 进 `openPositionPendingQuotes` Map（同 SYMBOL 覆盖去重），`socketStore.orderOperationEvents` 进 `pendingOrderEvents` 数组，两个独立 500ms `useIntervalFn` 分别 batch 送 worker，互不阻塞；
- **Worker 内全量重算 + 5 份索引**：`unfoldRows / foldRows / totalStats / categoryStats / statsBySymbol` 一次循环维护，5 类（buy/sell/profitable/losing/all）+ 按品种的二级统计同步推导；
- **同品种自动折叠 + 对冲识别**：用 Decimal.js 算加权开仓价、净手数方向（多/空/对冲）、累计 swap/commission/PNL，净仓位为 0 标记为对冲组（CMD=6），孤仓识别 `isNetPosition`；
- **分级 emit 策略**：`stats-updated` 立即推（账户面板秒级响应），`order-updated` 走 dirty flag + 500ms 节流（覆盖式只保留最新一帧，避免列表重排抖动）；
- **可视行联动订阅池**：表格 `handleVisibleDataUpdated` 在 rAF 内把"当前可视品种"推到 `socketStore.updateModulePool('OpenOrder', symbols)`，把 ws 推送量收敛到可视区；
- **关键性能护栏**：`unfoldRows / foldRows` 用 `shallowRef`（避免 1 万行 × 30 字段的深度 Proxy 创建）、`reactive` 仅用于统计；
- **切账号清理顺序协议**：先清 UI → 清 store → 清订阅池 → 清两条 batch 缓冲 → 重置统计 → 通知 worker `initOrder([])`，避免旧数据残留闪烁；
- **派生整个账户面板**：主线程 watch `totalFloatingPL`，按 `Equity = Balance + Credit + Commission + Swaps + FloatingPL`、`FreeMargin = Equity - UsedMargin`、`MarginLevel% = (Equity / UsedMargin) × 100` 实时推回 `accountsStore.updateAccountWithDynamicInfo`，让账户头部、保证金水平、可用保证金 等核心指标全部联动；
- **Worker 共享单例 + 热更释放 + 错误自愈**：`import.meta.hot.dispose` 自动 terminate，未捕获错误时 terminate 重建。
- **技术栈**：Vue 3 Composition API、Web Worker（module worker）、`shallowRef`、`@vueuse/core` `useIntervalFn`、Pinia、Decimal.js、TypeScript
- **业务价值**：CFD 经纪商客户端最重的 3 个数字（账户净值 / 可用保证金 / 保证金水平）和持仓表的盈亏全部跑在这条管线上。**支持万级订单 + 多品种（数十种）+ 报价高频推送**的实时刷新场景，主线程长任务清零；新开仓事件、报价 tick、改 SL/TP、改手数、平仓 等动作都能在亚秒级反映到 UI。
- **简历建议表述**：
\> 主导设计交易终端持仓与账户面板实时计算管线：以「报价/订单事件双 channel 独立 500ms 批处理 → Worker 全量重算 → 分级 emit（stats 实时 / orders 节流）」三段式架构支撑**万级订单 + 数十品种 + 高频报价**实时盈亏；引入 **`__profitFactor` 盈亏因子缓存**把币种/合约规模/汇率重计算降级为单次乘法，配合 Decimal.js 同品种自动折叠（加权开仓价、净仓位方向、对冲识别）；以 `shallowRef + 可视行联动订阅池` 控制主线程响应式开销与 ws 推送量；并将统计结果**派生为账户净值 / 可用保证金 / 保证金水平**，驱动整个客户端最关键的 3 个数字。
