# 浏览器的缓存机制

**浏览器缓存全景图：所有会影响请求的缓存头与机制**
**整体实现思路**
要把浏览器缓存看明白，最稳的办法不是死记头名，而是先建立一条判断链：

1. **先看是不是根本没走 HTTP 缓存机制**，例如命中了 bfcache 或被 Service Worker 接管；
2. **再看 HTTP 缓存有没有可复用条目**；
3. **再看条目是不是 fresh**；
4. **如果 stale，是否有验证器（ETag / Last-Modified）可做条件请求**；
5. **最后再看这次请求自己有没有用 Cache-Control 或 fetch(..., \{ cache \}) 把默认行为改掉。** HTTP 缓存本质上就是“请求头 + 响应头 + 浏览器缓存状态”三方一起决定的。([web.dev](https://web.dev/articles/http-cache))

**第一步：先分清 4 套“缓存/复用”机制**
**1）HTTP Cache**
这是最常说的浏览器缓存。浏览器会把“某个请求对应的响应”存起来，后续请求满足条件时直接复用，或者先做条件验证再决定要不要下载正文。Cache-Control、Expires、ETag、Last-Modified、Vary 这些头主要都在管它。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching?utm_source=chatgpt.com))

**2）bfcache**
这是**前进/后退缓存**，不是普通 HTTP 缓存。它保存的是**整页快照**，包括 DOM、JS 堆、页面状态；命中后，浏览器往返前进后退时可以瞬间恢复页面，不需要重新发起那一套网络请求。它和 HTTP cache 完全不是一回事。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Glossary/bfcache))

**3）Service Worker + Cache API**
Service Worker 像一个运行在浏览器里的代理，可以拦截请求，自己决定是直接走网络、先查 Cache API、还是返回自定义响应。也就是说，它可以**覆盖或绕开**浏览器默认的 HTTP cache 决策。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers))

**4）浏览器主动改写缓存行为**
浏览器普通访问、刷新、强制刷新，以及 fetch(..., \{ cache \}) 的不同 cache mode，都会改变这次请求如何使用 HTTP cache。尤其 Request.cache 的 default、no-store、reload、no-cache、force-cache、only-if-cached，会直接改变“先不先查缓存、是否必须重验证、是否回写缓存”。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/API/Request/cache))

**第二步：浏览器判断缓存时，真正的顺序是什么**
**第 1 关：先看是否被别的机制短路**
如果这次是浏览器“后退/前进”恢复页面，优先可能命中 bfcache；如果有 Service Worker 拦截，也可能直接走它自己的逻辑。只有这些都没有接管时，才进入普通 HTTP cache 决策。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Glossary/bfcache))

**第 2 关：看有没有“可匹配的缓存条目”**
HTTP cache 不是只看 URL。标准匹配至少会受 **方法 + URL + Vary 指定的请求头**影响。若缓存响应带了 Vary: Accept-Encoding, Accept-Language，那下次请求只有这些请求头也匹配时，浏览器才可以直接复用该缓存条目；如果 Vary: *，那这个条目总是匹配失败，不能直接复用。([RFC Editor](https://www.rfc-editor.org/rfc/rfc9111.html))
==Vary 是一个 HTTP 响应头，意思是“缓存时，要考虑这些因素”。同样的网址，对不同的人，可能返回不同的内容。缓存服务器不能只存一份，要区分对待。==
**第 3 关：看这个缓存条目是不是 fresh**
freshness 的优先顺序可以这么记：

1. 对**浏览器私有缓存**，优先看响应里的 Cache-Control: max-age=...。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control))
2. Expires 只在没有 max-age 时才有意义；一旦有 max-age，Expires 必须被忽略。([RFC Editor](https://www.rfc-editor.org/rfc/rfc9111.html))
3. Age 表示这个响应在缓存链路里已经“老了多少秒”，浏览器会把它算进响应年龄。([RFC Editor](https://www.rfc-editor.org/rfc/rfc9111.html))
4. 如果没有显式过期信息，规范允许浏览器做**启发式缓存**；常见做法会参考 Last-Modified，规范举例里提到“约 10% 的时间差”是典型策略。([RFC Editor](https://www.rfc-editor.org/rfc/rfc9111.html))

**第 4 关：如果 stale，看能不能做条件请求**
==Stale 在缓存语境下，意思是“过期的/陈旧的”。这份缓存已经“过期”了，但还没扔掉，先凑合用着。==
如果缓存条目过期了，但响应里有验证器，浏览器会发**条件请求**：

- 有 ETag 时，通常带 If-None-Match。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching))
- 没有 ETag，但有 Last-Modified 时，通常带 If-Modified-Since。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Last-Modified?utm_source=chatgpt.com))
- 两者同时存在时，If-None-Match 优先级高于 If-Modified-Since。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching))

如果服务端判断内容没变，就回 304 Not Modified，浏览器继续用本地副本；如果变了，就回 200 和新内容。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching))

**第 5 关：看这次请求自己有没有“强行改规则”**
即使缓存条目是 fresh，请求端也可能主动改规则：

- fetch(url, \{ cache: "no-store" \})：完全绕过 HTTP cache，也不写回缓存。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/API/Request/cache))
- fetch(url, \{ cache: "reload" \})：不先查缓存，但网络结果会回写缓存。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/API/Request/cache))
- fetch(url, \{ cache: "no-cache" \})：即使本地有缓存，也会走条件请求验证。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/API/Request/cache))
- fetch(url, \{ cache: "force-cache" \})：有缓存就直接用，哪怕 stale。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/API/Request/cache))
- fetch(url, \{ cache: "only-if-cached" \})：只允许命中 HTTP cache；没有缓存就返回 504，而且只能用于 same-origin。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/API/Request/cache))
